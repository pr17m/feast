# Feast mobile apps (iOS and Android)

Two store apps wrap the live Feast web app with [Capacitor](https://capacitorjs.com) 8:

| App | Store name | Bundle / application ID | Opens | URL scheme |
| --- | --- | --- | --- | --- |
| `diner/` | **Feast** | `com.feast.diner` | `/` (discover, book, pay) | `feast://` |
| `partner/` | **Feast Partner** | `com.feast.partner` | `/partner` (restaurant owners) | `feastpartner://` |

The admin app stays on the web (it's for the Feast team only).

> **No store needed: install from the browser.** The same two apps also install straight from the website — "Install" in Chrome/Edge/Android, or Share → Add to Home Screen on iPhone/iPad — with an offline page and update prompts. See "Install as an app" in `webapp/README.md`. The store apps add push notifications, the QR scanner and store presence.

## How it works

1. The app starts on a small page bundled inside it (`shared/www`): the **country picker** ("Australia" / "India"). The choice is remembered (Capacitor Preferences) and can be changed later from the app (footer in the diner app, sidebar in the partner app → **Change country**).
2. It then opens that country's **live site** (from `shared/countries.json`) inside the app. Every web release reaches the apps at once — no store update needed for web changes.
3. On the live site, the web app talks to the phone through Capacitor's native bridge (`webapp/src/lib/native.ts`):
   - **Push notifications** (Firebase Cloud Messaging on both iOS and Android): after sign-in the app asks for permission and registers the device with `POST /v1/me/push-tokens`; sign-out removes it (`DELETE /v1/me/push-tokens/{token}`). Tapping a notification opens the page in its `data.path`.
   - **QR scanner**: "Scan restaurant QR" on the home and *At the restaurant* pages (diner app). Feast codes (`/r/{code}`, old `/t/{code}`) open in the app.
   - **Links**: Feast links (https universal links / app links, `feast://…`, `feastpartner://…`) open the right page in the app.
   - Status bar, splash screen, Android back button, offline page (`offline.html`, shown when the site can't be reached).
4. Other sites (e-mail, maps, anything not in `countries.json`) open in the system browser. Card payments (Stripe, Razorpay) stay in the app.

> **Android detail.** On iOS Capacitor exposes its bridge to every page. On Android it only does so for bundled pages, so `MainActivity` adds it to the country sites listed in `allowNavigation` (exact hosts only — never the wildcard payment hosts). This is generated by `shared/configure-native.mjs`.

## What's in this folder

```
mobile/
  package.json            npm workspaces + scripts (run everything from here)
  shared/
    countries.json        ← YOUR LIVE SITES (one per country)
    apps.json             app names, bundle IDs, start paths, URL schemes
    www/                  the bundled start page (picker, offline page)
    assets/               icon + splash sources (SVG and PNG)
    build-www.mjs         builds diner/www and partner/www from www/ + config
    configure-native.mjs  applies Feast's native settings to ios/ and android/
    build-assets.mjs      copies icon/splash sources for @capacitor/assets
    check.mjs             CI check (no Xcode / Android SDK needed)
  diner/   capacitor.config.ts, ios/, android/
  partner/ capacitor.config.ts, ios/, android/
```

`ios/` and `android/` are real native projects and are committed. Don't edit the parts between `feast:` markers by hand — change `shared/*` and run `npm run build`.

## One-time setup

### Accounts (you)

1. **Apple Developer Program** — enrol as an **organisation** (needs a D-U-N-S number for your company). Then in App Store Connect create two apps with bundle IDs `com.feast.diner` and `com.feast.partner`.
2. **Google Play Console** — create an **organisation** developer account (also D-U-N-S). Organisation accounts can publish without the 12-testers-for-14-days closed test that new personal accounts need. Create two apps.
3. **Firebase** (free) — one project with four apps: iOS `com.feast.diner`, iOS `com.feast.partner`, Android `com.feast.diner`, Android `com.feast.partner`.
   - In Apple Developer → Keys, create an **APNs key** and upload it in Firebase → Project settings → Cloud Messaging (for both iOS apps).
   - Download `GoogleService-Info.plist` (iOS) and `google-services.json` (Android) for each app and put them here — they are **git-ignored**, never commit them:
     - `diner/ios/App/App/GoogleService-Info.plist` and `partner/ios/App/App/GoogleService-Info.plist` (also drag each into the App target in Xcode once)
     - `diner/android/app/google-services.json` and `partner/android/app/google-services.json`
   - The API sends pushes with Firebase's service account — see the backend's push settings in `deploy/` (the server must include `data.path`, e.g. `/bookings/bk_123`, in each message so a tap opens the right page).

### Your Mac

- **Node.js 20+** (`brew install node`)
- **Xcode** — the current release from the Mac App Store (Apple only accepts uploads built with the latest SDK). Open it once to install components.
- **CocoaPods** — `brew install cocoapods` (the QR scanner plugin needs it)
- **Android Studio** — current release (it bundles JDK 21, which these projects need). In its SDK Manager install **Android 16 (API 36)** SDK and build tools.

### Fill in your sites

Edit `shared/countries.json` with your live https sites (no trailing slash), e.g.

```json
{ "code": "au", "name": "Australia", "flag": "🇦🇺", "url": "https://au.feast.app" }
```

Then, from `mobile/`:

```bash
npm install
npm run build        # rebuilds the start page and native settings (app links use your hosts)
npm run sync         # copies everything into ios/ and android/ and runs pod install
```

Commit the changes `npm run build` makes to `ios/` and `android/`.

### Universal links / app links

So that tapping a Feast link (e.g. a restaurant QR code) opens the app instead of the browser, each country site must serve:

- `https://<site>/.well-known/apple-app-site-association` — with your Apple **Team ID** and the two bundle IDs
- `https://<site>/.well-known/assetlinks.json` — with the two package names and the **SHA-256 fingerprints of your app signing keys** (Play Console → Test and release → App integrity → App signing)

The web app serves both files; set the Team ID and fingerprints in the web deployment's settings (see `deploy/compose/README.md`). Until then links simply open in the browser.

## Android release

1. **Upload key** (once per app) — keep it and its passwords safe (a password manager), never in git:
   ```bash
   cd diner/android
   keytool -genkey -v -keystore feast-diner-upload.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
   ```
   Create `diner/android/keystore.properties` (git-ignored):
   ```properties
   storeFile=feast-diner-upload.jks
   storePassword=…
   keyAlias=upload
   keyPassword=…
   ```
2. In Play Console turn on **Play App Signing** (Google holds the app signing key; you upload with the upload key).
3. Bump `versionCode` (must increase every upload) and `versionName` in `diner/android/app/build.gradle`.
4. `npm run aab:diner` and upload `app-release.aab` to **Internal testing** → install from the Play link on a phone → **Closed testing** → **Production**.
5. For quick testers outside Play: `npm run apk:diner` and share `app-debug.apk` (they must allow installs from unknown sources). The Play Store only takes `.aab`.

Targets Android 16 (API 36), which Google Play requires for new apps and updates since 31 Aug 2026.

## iOS release

1. `npm run sync` then `npm run open:diner:ios` (opens `App.xcworkspace`).
2. Target **App** → Signing & Capabilities: choose your **Team**; keep bundle ID `com.feast.diner`. Check that **Push Notifications** and **Associated Domains** (`applinks:<your hosts>`) appear — they come from `App/App.entitlements`.
3. Set **Version** (e.g. 1.0) and **Build** (increase every upload).
4. Product → Archive → Distribute App → App Store Connect → Upload.
5. In App Store Connect: test with **TestFlight** (internal testers first), then fill in the listing and submit for review.

The iOS apps are **iPhone-only** (no iPad screenshots or iPad review needed). Minimum iOS 15.5.

## Before you submit (both stores)

- [ ] Production site per country: real domain with https, `FEAST_ENV=production`, real SMS codes (Twilio), live Stripe/Razorpay keys.
- [ ] Policy pages with your company details, reviewed by a lawyer (`FEAST_LEGAL_*` settings) — the stores need the privacy policy URL: `https://<site>/legal/privacy`.
- [ ] **Account deletion in the app**: Account → **Delete my account** (both stores require it).
- [ ] **No in-app purchase of restaurant subscriptions.** Inside the apps the Partner subscription page shows the plan only; owners subscribe on the website. (Meals are real-world services, so card payment through Stripe/Razorpay is allowed.)
- [ ] **Sign-in in the apps is by phone code** (owners: email + password). Google and Facebook block sign-in inside an app's web view, so the apps hide those buttons; that also means Apple's "Sign in with Apple" rule doesn't apply. Adding native Google/Apple sign-in is a later step.
- [ ] **Review accounts** for Apple and Google (see the template below). The API supports fixed review phone numbers (`[auth.otp] review_numbers`) so reviewers can sign in without receiving an SMS.
- [ ] Push notifications tested on a real device (TestFlight build / internal test track).
- [ ] Screenshots, descriptions and privacy answers (below).

### Apple — App Privacy (draft from what Feast collects; check before submitting)

| Data type | Collected | Linked to the user | Used for | Tracking |
| --- | --- | --- | --- | --- |
| Name, email address, phone number | Yes | Yes | App functionality | No |
| Purchase history (bookings, bills, deals) | Yes | Yes | App functionality, analytics (in-app insights) | No |
| Photos (complaint attachments; owners: dish photos, licence documents) | Yes, optional | Yes | App functionality | No |
| Customer support / other user content (reviews, complaint messages) | Yes | Yes | App functionality | No |
| User ID, device ID (push token) | Yes | Yes | App functionality | No |
| Coarse location (country from IP address) | Yes | No | App functionality | No |
| Payment card details | No — entered into Stripe/Razorpay, never stored by Feast | | | |

No data is used for tracking or sold. No third-party advertising.

### Google Play — Data safety (draft)

- **Data collected**: Personal info (name, email, phone); Financial info (purchase history); Photos (optional); Messages (in-app messages with restaurants/support); App info and performance (server logs); Device or other IDs (push token); Approximate location (country from IP).
- **Shared**: with the restaurant you book/pay (name, phone, booking and order details) and with payment processors to complete payments — both "for app functionality".
- **Security**: data encrypted in transit; users can request deletion (in app: Account → Delete my account; web: same page).
- Card numbers are handled by the payment processor's form and not collected by Feast.

## Known limits

- **Apple Pay / Google Pay**: the Stripe payment form runs inside the app's web view, where card entry works. Apple Pay is switched off by iOS in web views that have injected scripts (Capacitor's bridge is one), and Google Pay in an Android web view needs extra setup and may not appear — so in the apps diners pay by card. Adding Stripe's native payment sheet (Capacitor plugin) is the next step if you want Apple Pay / Google Pay in the apps.
- **Google / Facebook sign-in** are hidden in the apps (see above).
- **Offline**: the apps need a connection; without one they show the offline page.
- The country picker lists the countries in `countries.json`; add New Zealand, Canada, UK by adding entries and rebuilding.

## Troubleshooting

- *"This build isn't set up yet"* — `countries.json` still has `.example` URLs; fill them in, `npm run build`, `npm run sync`, rebuild.
- *No push on iOS* — check the APNs key in Firebase, `GoogleService-Info.plist` is in the App target, and you're testing on a real device (not the simulator).
- *Links open the browser, not the app* — the site's `.well-known` files are missing or have the wrong Team ID / fingerprint; on Android check with `adb shell pm get-app-links com.feast.diner`.
- *`pod install` errors* — `cd diner/ios/App && pod repo update && pod install`.
